Versioning and deprecation

The interface is versioned in the URL path: {{ api.base_path }}/** keeps its response shapes, and a breaking change ships as /v2/** beside it rather than replacing anything in place. The unversioned paths (/raw/**, /llms.txt, /openapi.json) predate the prefix and are maintained as aliases of the v1 shapes. Two versions travel with the interface and answer different questions: api_version ({{ api.api_version }}) is the shape, corpus_version ({{ api.version }}) is the content.

Compatible, shipped without notice: {{ api.versioning.compatible_changes | join: '; ' }}. Breaking, and therefore never done inside {{ api.base_path }}: {{ api.versioning.breaking_changes | join: '; ' }}.

A retiring endpoint says so in its own responses: Deprecation (RFC 9745) carries the date the deprecation took effect, Sunset (RFC 8594) the date it stops answering — never less than {{ api.versioning.sunset_notice_days }} days later — and a Link with rel="deprecation" points at what replaced it. Live deprecations are listed in /v1/version.json, which is the field to poll: {% if api.deprecations == empty %}it is empty today — nothing here is deprecated{% else %} {{ api.deprecations | size }} endpoint(s) are being retired{% endif %}.

Rate limits

The static origin does not throttle. Where the optional edge tier is deployed in front of it, the quota is {{ api.rate_limit.quota }} requests per {{ api.rate_limit.window_seconds }} seconds per {{ api.rate_limit.partition }}, advertised on every response in the RateLimit header fields: 

RateLimit-Policy: {{ api.rate_limit.policy }}

Over the quota: 429 with Retry-After in seconds and a problem body of type rate_limited. {{ api.rate_limit.advice }}

Errors

Error responses follow RFC 9457 problem details, with two extension members: code, stable for matching, and resolution, saying what to do next. Every type is also published as a document you can read without provoking it — /v1/errors/index.json for the catalogue, /v1/errors/<code>.json for one. Because the site is served as static files, a client that asks for HTML gets the 404 page, which carries the same problem details in a <script type="application/problem+json" id="problem"> element and a markdown recovery block, also served on its own at /404.md.

Markdown variants

Every page that has a markdown twin links it with <link rel="alternate" type="text/markdown">, and the mapping is mechanical, so an agent can rewrite a URL instead of parsing HTML:

PageMarkdown
/reviewers/<slug>/ /raw/<slug>.md
/domains/<domain>/ /raw/bundles/<domain>.md
/ /raw/site.md
whole corpus /llms.txt

Static hosting cannot vary a response on the Accept header, so Accept: text/markdown against an HTML page on this origin returns HTML. Follow the rel="alternate" link, or rewrite the path, to get markdown. Behind the edge tier the same URLs answer Accept: text/markdown directly, with Content-Type: text/markdown; charset=utf-8 and Vary: Accept so caches keep the two variants apart, per acceptmarkdown.com.

JSON representations

Everything under {{ api.base_path }} is typed JSON, described by schema in /openapi.json: the corpus index, the domains, the facets (every topic, language and repository with counts), the source repositories, the error catalogue, and one document per instruction carrying its metadata, its markdown body and its links. An instruction page also advertises its JSON with <link rel="alternate" type="application/json">. 

# the instruction behind a page, as JSON
curl -s {{ site.url }}{{ api.base_path }}/instructions/{{ first.slug }}.json | jq '{title, domain, updated}'

# every Python instruction about concurrency
curl -s {{ site.url }}{{ api.base_path }}/index.json \
  | jq -r '.entries[] | select(.language == "Python" and .topic == "Concurrency") | .json'

# what the interface guarantees, and what may change
curl -s {{ site.url }}{{ api.base_path }}/version.json | jq '.versioning, .rate_limit'

Discovery

Four files describe this interface, and every page links them, so a client that lands anywhere can find the rest without crawling:

FileWhat it isLink relation
/openapi.json OpenAPI 3.1 description of every endpoint service-desc
/v1/version.json Version, versioning and deprecation policy, quota, resource list service-meta
/.well-known/api-catalog RFC 9727 catalogue, as an RFC 9264 linkset api-catalog
/agents.md When to use this corpus, when not to, and what to call help

Static hosting serves the extensionless catalogue without the profile media-type parameter RFC 9727 recommends; the edge tier sets it, and the catalogue links RFC 9727 as describedby either way.

CLI

A single file, Python 3.9+, no dependencies — the same endpoints, with the paging and the change detection already written: 

curl -sSO {{ api.cli }}
chmod +x awesome-reviewers.py
./awesome-reviewers.py search "kv cache" --limit 5
./awesome-reviewers.py bundle llm-infra -o rubric.md
./awesome-reviewers.py sync ./corpus --domain security

Source in cli/. It is not on a package registry yet, so there is nothing to install — see the developer portal.

# assemble a system prompt from one domain
curl -s {{ site.url }}/raw/index.json \
  | jq -r '.entries[] | select(.domain == "orchestration") | .raw' \
  | xargs -n1 curl -s > orchestration.md

Freshness

Every instruction carries the date of the most recent review comment behind it, and every domain carries the newest date among its instructions. Both are exposed in /raw/index.json and in the front matter of each raw file, so a scheduled job can diff against its last run instead of refetching the corpus.

The corpus was last updated {{ site.data.domains.updated }} ({{ site.data.domains.updated }}).

From the repository

If you would rather not fetch over HTTP, the source of truth is _reviewers/: one markdown instruction per file, plus a sibling JSON file holding the review discussions it was derived from. Clone it and run python build_data.py to regenerate every artifact listed above locally.
