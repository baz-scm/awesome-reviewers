awesome-harness

A coding harness with six machine-enforced pillars, whose policy layer is compiled from this corpus. 35 instructions from 14 repositories shaped it: 16 became coded checks, 20 decided how its own internals work. Every one of them is linked below.

It lives in harness/. Python standard library only, no install step, no build. It is not part of this site. 

harness/awesome-harness gate       # evaluate the corpus against your working change
harness/awesome-harness context    # the instructions that apply to the files you touched
harness/awesome-harness run harness/plans/gate-only.json
harness/awesome-harness verify

Where it came from

The design is inspired by awslabs/aidlc-workflows, which gives an AI coding agent a three-phase workflow — inception, construction, operations — with blocking review gates and human approval between phases. That shape is good, and the harness keeps it.

What differs is where enforcement lives. AI-DLC's verification is prose the model is asked to honour. The harness supplies the substrate underneath: the gate is code, the history is hash-chained, the approval binds to a tree digest, and a run ends in a signed statement naming the policy version that gated it.

There is a pleasing recursion in the sourcing. This corpus contains 23 instructions distilled from review discussions on aidlc-workflows itself, because that project's reviewers had already worked out what is hard about building an agent harness. 20 of those 23 are cited in the harness's source, in the module whose behaviour they decided.

The idea

A harness needs a policy layer, and a policy layer needs rules that a team will actually accept. Invented lint rules do not survive contact with a code review. Rules traceable to the discussion that produced them do, which is what makes a corpus of distilled review feedback the right source.

So a policy pack selects instructions from the corpus, pins each one by the digest of its body, and carries a digest of its own. That pack digest feeds the cache key and the attestation. Given an attestation you can say which version of which rule, sourced from which review discussion, gated a particular change — and check it, because the pack is committed and the corpus is public.

Enforcement has two tiers, and the split is the honest part:

  • machine — 16 coded checks, each bound to the instruction it enforces. policy build refuses to compile a check whose slug does not resolve to a real instruction file, because a rule citing something that does not exist enforces nothing while looking identical to one that does.
  • advisory — the instruction body, delivered as review context for the changed files that match its language. 16 checks out of 5,000+ instructions is the true ratio: almost all of this material is judgement a reviewer applies, and no checker will ever decide “name things for what they do”. The harness's job for that majority is to put the right instructions in front of whoever reviews next, and to record which ones it delivered.

The six pillars, and what the corpus decided

1. Source control — durable, immutable history of how code evolved

Git is already the immutable history. Two things it does not give you.

Work that is not a commit yet. An agent's output exists as a dirty worktree long before it is a commit, and that is exactly the window you want recorded. snapshot writes the working tree into real git objects through a temporary index — write-tree then commit-tree — and anchors the result at refs/harness/snapshots/<run-id>. Nothing is staged, no branch moves, no commit lands on any branch, and the state becomes a content-addressed object git will not collect.

A record of the process. The ledger is append-only JSONL where each record's digest covers the previous record's digest, so editing or removing record n invalidates every record after it and verify says which one. It is committed to git: the record of how the code was made is as durable as the code.

Single-Transaction Locking decided the write path. Reading the ledger tail and appending its successor happens inside one flock; split them and two concurrent writers build two chains from the same predecessor — a fork that verify would report but no repair could untangle. Scoped Hash-Based Idempotency decided how it is read: an append-only ledger keeps every previous attempt, so “has this stage converged?” answered over all of history says yes on the strength of a run from yesterday against different code. Ledger.since_stage_start exists because of that sentence, and floors every such query at the latest STAGE_STARTED for the current stage run.

2. Execution — isolated, performant compute for building and validating changes

Steps run in a detached worktree of an immutable commit. The container backend drops all capabilities, disables the network, runs as a non-root uid under a read-only root filesystem with pids and memory caps, and passes secrets through --env-file rather than -e, which docker inspect exposes to any user on the host. The local backend uses a fresh session plus setrlimit, and a timeout kills the process group, not just the child.

Secure Path Confinement is the instruction the container flag set is taken from, almost line by line — drop capabilities, cap resources, avoid root via the calling uid, and scrub credentials from stdout and stderr before returning or logging them. Scrubbing happens on the way into storage rather than on the way out to a screen, because step output is persisted in the run folder, hashed into the artifact store, and summarised in the ledger; there is no later point at which redaction helps.

Explicit Environment Contracts is why a step sees an allowlist and never os.environ wholesale, and why the allowlist replaces rather than appends — an env_allow that only ever added could never remove an inherited variable, which is the whole point of an allowlist. Sandbox config boundary is why isolation is resolved once into a reported structure rather than re-derived at each use site, and why that structure is what the attestation carries.

Fail Loudly, Degrade Safely decided the backend policy. auto may fall back from container to local and records the reason verbatim; container refuses rather than substituting. And the local backend's isolation report says "network": "host (not isolated)", because claiming otherwise in a record designed to be handed to someone else would make the record a lie.

3. Artifacts — reproducible outputs that move across systems

A content-addressed store, manifests digested excluding their own timestamp, and bundles that are byte-identical anywhere. Every tar field a writer would otherwise take from the ambient system is pinned: mtime=0, uid and gid 0, empty uname and gname, member order sorted, permissions normalised to 0644/0755.

Deterministic Boundary Modeling is why: the bundle is a boundary, so pin every field a reader could observe. The same instruction is why there is exactly one canonical serialization for every digest in the package — if two code paths hashed “the same” object differently, every guarantee built on digests would quietly degrade to a guess.

Executable Documentation Accuracy turned that claim into a plan step. harness/tools/determinism_check.py builds the same bundle twice under a changed umask, changed mtimes, a changed timezone and a different working directory, and fails the run if the digests differ. A documented guarantee that nothing executes is a guarantee that quietly stops being true.

No Silent Null Artifacts is why publishing a zero-byte artifact is an error unless the step declared allow_empty, and why a required output that matched nothing fails by name rather than reporting “no files matched”. An empty output that reaches production looking like success is the failure mode.

Prevent path traversal governs import: a bundle is the one input arriving from a machine this process does not control, so every member name is validated before extraction, every member is re-hashed against the digest the manifest asserts, and a member the manifest does not list is rejected rather than ignored — an unlisted member is how you smuggle a file into a “verified” bundle.

4. Caching — reuse of deterministic work

The key covers the step's argv, cwd, declared environment and outputs; the digest of every declared input file; a fingerprint of every declared tool version; a digest per environment value; the policy pack digest; the platform; and the resolved isolation backend — for a container, the image digest, never the tag, because a tag is a mutable pointer and a cache keyed on python:3.11-slim silently spans every toolchain that tag ever addressed.

Deliberately excluded: the run id, timestamps, the actor, the ledger head, the hostname, absolute paths, and HOME/TMPDIR, whose values are per-run by construction. Each of those changes between two runs that should hit, so including any one produces a cache with a permanent 0% hit rate — which looks exactly like a working cache until someone measures it.

Scoped Hash-Based Idempotency is the single most load-bearing instruction in the harness, and it appears in five modules. Its three rules map directly onto three refusals: key by content and not identity, so a step declaring no inputs cannot be cached and says so rather than replaying its first result forever; detect same-key conflicts and fail loudly, so one key addressing two input sets raises and never resolves by preferring a side; and scope completion signals to the current run window, which is why content reuse legitimately crosses runs while “this stage already finished” does not.

The same instruction produced a fourth refusal, and this one was found by CI rather than by reading. A container whose image digest cannot be resolved is not cacheable, because docker run on a missing image pulls it and thereby supplies the digest that was absent a moment earlier — so run two computes a different key from identical inputs, and the cache reports a permanent miss while looking like it works. Keying on the tag instead would be worse, spanning every image that tag ever pointed at. The digest is resolved once per process for the same reason, which is Sandbox config boundary — resolve the sandbox's configuration once and report it — applied properly rather than merely claimed.

No Silent Null Artifacts is why a hit whose blobs have been evicted is reported as a miss, rather than handing the caller a manifest pointing at nothing. Defensive Observable Error Handling is why a miss names the input that moved instead of merely being reported.

5. Identity — proving who or what produced code

The pillar turns on one distinction most provenance tooling blurs. A claim is what the environment says — git config user.email, CLAUDECODE=1, GITHUB_ACTOR — all writable by whoever runs the process. A proof is a signature verifying against a key in a committed allowed-signers file. An attestation records both, in separate fields, and never promotes one to the other.

Security Trust Boundaries is the reason. An environment variable crossing into a security decision is untrusted input, so the harness records which variable it observed alongside the claim it produced, and lets the reader weigh it. Fail Loudly, Degrade Safely is why no signer configured is a labelled state written into the file itself — a reader who never runs verify still cannot mistake an unsigned record for a signed one — and why unsigned, unverifiable and invalid are three different answers that stay three different answers. There is no code path that reports verified without having checked a signature. An unsigned record is merely weak; a fabricated one poisons every record beside it.

Secure Scope and Input Validation — verify before trusting — is why the payload is parsed from the envelope it was signed over rather than from a convenient copy beside it, and why the verifier takes the signing principal from the statement and never from a flag. A caller who supplied the principal would be choosing whose signature counts.

Avoid Logging Sensitive Data is why a CI token's presence is recorded and its value never is, and why argv is scrubbed before it enters the ledger — --token=… looks harmless while you are typing it and is permanent once chained.

6. Policy — machine-enforceable rules for quality, security and compliance

Pinned Releases For CI is the pack model: pin what you depend on, because a floating reference is not a version. Each rule records the digest of its instruction body, and Behavior-Correct, Versionless Docs is why drift is named rather than tolerated: policy verify reports a rule whose source instruction changed since the pack was built and exits non-zero, so the pack gets rebuilt deliberately with the new digest recorded instead of drifting under a signature.

Check mode must mirror set the bar for the checks themselves: a check must decide exactly what its rule says, or it teaches people that the gate is noise. That instruction is directly responsible for the four narrowings described below. It also shaped verify, which re-derives what the runner asserted rather than reading back its own JSON — if the same code did both, a serialization bug would verify itself.

Portable Configuration Standards is why the corpus is read from _reviewers/ or from a download of the raw endpoints, and never from this site's derived _data/ — those files are generated and uncommitted, and depending on them would make the harness require a site build. Use scoped, consistent names is why a finding's fingerprint covers check, path and normalized evidence but excludes the line number: inserting an import above a violation must not present it as a new violation, or two runs cannot be compared.

Findings are scoped to added lines. A gate that reported whole files would blame every change for the state of the repository and be switched off within a week.

What the corpus caught in the harness's own code

The first time the gate ran against the harness, it fired on the harness. Some of those findings were real, and some were the checks failing to decide what their instructions actually say — which is Check mode must mirror in the negative. Four checks were narrowed as a result, each narrowing justified by re-reading the source instruction rather than by wanting a green build:

  • AH008 fired on s.get("name"), a dictionary lookup, because s had been listed as a plausible HTTP receiver. Narrowed to unambiguous clients plus a URL-shaped first argument. s.get on a dict is far more common than an HTTP call, and a check that fires on it gets the gate switched off.
  • AH010 fired on os.environ["TZ"] = "UTC", which is a write, and on os.environ[name] already guarded by if name in os.environ. Narrowed to reads with a constant key — which is the hardcoded required-variable read the instruction is actually about.
  • AH005 fired on str(x).startswith("https://") and on name.startswith("/"), an absoluteness test. Narrowed to require path-ness in the receiver, in the prefix, or an absolute prefix naming an actual directory — the rule is about containment, and a bare "/" check is a different and legitimate operation.
  • AH011 fired on logging.info("key of %d chars", len(api_key)), which discloses a length. Narrowed to stop descending into calls that consume a value without printing it.

It also fired, correctly, on the harness's own test fixtures — which carry deliberately provider-shaped strings so that AH001 can be shown to fire — and then on the waiver written to excuse them, because that waiver's stated reason quoted the example key. Both are recorded in .harness/waivers.json with a reason, which is the mechanism working rather than failing.

Two implementation bugs came out of reading the corpus rather than running it. The cache collision guard, as first written, compared two digests and could therefore only have fired on an actual SHA-256 collision — dead code dressed as a safety check. Re-reading Scoped Hash-Based Idempotency — detect same-key conflicts and don't fail silently — made the right comparison obvious: check the recorded inputs against the current ones, which catches the case that really happens, a non-deterministic field creeping into the key function. And the snapshot originally included .harness/, so the ledger's own growth changed the snapshot tree digest, silently voiding every approval the moment the approval itself was recorded.

What was not used

Three of the 23 aidlc-workflows instructions are not cited. CI security defaults overlaps almost exactly with the instruction AH003 is bound to; grafana's was chosen so the check set draws on more source repositories, and either would serve. Secure-by-default integrations is about configurable external services and plugin registries, which the harness does not have — it has no network surface at all. Concise, factual instructions governs how agent-facing instruction text is written; it applies to this corpus's own prose more than to the harness's code.

Recording the misses matters as much as the hits. A page that claimed every instruction had been applied would be the same category of thing as a check that cites an instruction which does not exist.

Using it

The harness works against a vendored corpus or against the raw endpoints, so it runs in any repository, offline, with no dependencies: 

harness/awesome-harness init
harness/awesome-harness policy build --topic Security --topic CI/CD --language Python
harness/awesome-harness gate --base origin/main

harness/README.md documents every command, the exit-code contract, and the plan format. harness/AGENTS.md is written for an AI agent driving it — including the instruction not to approve a human-gated phase on the user's behalf.
